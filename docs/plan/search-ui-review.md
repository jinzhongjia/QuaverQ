# UI 布局设计审查（代码层，待截图复核）

## 任务描述

以专业 UI 设计师视角审查 QuaverQ 的 QML UI 布局与视觉设计，对照两份基准：

- `qt-ui-design` skill 的桌面端审计清单（UX 法则 + WCAG 2.2 + 动效 / 排版 / 键盘规范）
- `qq-music-design` skill 的 QQ 音乐 PC 端设计规范 + 官方参考截图（`01~12-*.webp`）

本轮为**代码层静态审查**（通读全部 29 个 QML 文件 ≈7400 行 + token 定义），对比度数值为按 WCAG 相对亮度公式计算的精确值。涉及实际渲染效果的结论（字形图标观感、宽窗布局、暗色二维码等）需第二轮截图复核，见文末清单。

结论分级沿用审计规范：**Critical**（违反核心 UX 法则 / WCAG，必须修）、**Warning**（摩擦 / 认知负担，应该修）、**Opportunity**（增强项，可考虑）。

---

## 总体评价

地基相当扎实，问题集中在上层：

**做得好的**（同类自研项目里少见）：

- Token 纪律严格：组件层几乎零裸 hex / 裸字号（仅 LyricPanel 灰阶行、PlayerBar 角标 10px 等个别漏网），换肤确实只动 `Palette.qml`。
- 无障碍底子好：几乎所有交互组件有 `Accessible.role/name`、focus ring、`Keys.onReturn/Space`，44px 命中区有统一常量。
- 自绘窗口 chrome 完成度高：八向 resize、最大化去圆角、激活/失焦边框分色。
- 空态文案多数有引导（"登录后在这里看到你的歌单"、"输入关键词后按 Enter"）。

**核心问题**：4 个 Critical（正在播放页无出口、品牌绿对比度、窄窗功能截肢、无账号身份），以及一批"五套加载样式 / 三份 tab 实现已漂移"式的一致性债。

### C1. "正在播放"页进得去、退不出来，且摧毁导航栈

- 入口 `navigate("now-playing")` 走 `resetContent`（`Main.qml:113-115`）：**清空整个导航栈**再 push，于是 `contentStack.depth === 1`。

## Warning（应该修）

### W1. 播放键不在中轴线上

中央控制组是 模式 | 上一首 | **播放** | 下一首 共 4 个（`PlayerBar.qml:242-312`），整组居中后播放键落在中轴右侧约半个按钮位，与下方进度条的视觉中心错位。QQ 音乐是 循环|上一首|播放|下一首|音量 5 个对称排布。**建议**：补第 5 个元素（音量图标或歌词开关挪进来）或加等宽占位，让 52px 绿圆正好压在进度条中点上方。

### W2. 图标按钮没有 ToolTip

`IconButton.qml` 的 `text` 只进了 `Accessible.name`，明眼用户 hover 没有任何提示。而字形本身又偏密码学：`⇄`(顺序) `↻`(列表循环) `①`(单曲循环) `⇋`(随机) `词` `☰`。在 `IconButton` 里加三行 `ToolTip.visible: hovered; ToolTip.delay: 600; ToolTip.text: control.text` 一处修全部。

### W3. 同一个 tab 控件复制了三份，且已经漂移

SearchView / LibraryView / DetailView 各自内联实现了"文字 + 2px 下划线" tab：SearchView 高 36、文字无 topMargin；另两处高 38、topMargin s2。三个页面的 tab 基线肉眼可见地不一致。抽成 `components/TabRow.qml`。tab 命中区也只有文字宽 × 38px，偏窄，组件化时顺手加左右 padding。

### W4. 加载状态五套并存，首页冷启动甚至是"无声空白"

| 位置 | 加载表现 |
|---|---|
| HomeView 各 section | **什么都没有**（loading 时空态文案也隐藏） |
| DetailView / SongDetailDialog | 默认样式 BusyIndicator（Basic 光板样式，与品牌脱节） |
| LibraryView | 纯文字"正在同步" |
| SearchField | 按钮文案换成"搜索中" |
| PlayerBar | 元信息行文字"正在准备播放链接" |

SWR 缓存让二次启动无感，但首次启动 / 缓存失效时首页是几个标题下挂着空白，违反 Doherty 阈值（400ms 内要有反馈）。**建议**：统一两种形态——内容区用骨架占位（卡片灰块 / 行灰条，QML 矩形 + 微呼吸动画即可），按钮内用小 spinner；BusyIndicator 自绘成品牌色。

### W5. 列表行交互缺桌面端常规通道

- SongRow 只有左键（点击即播）+ "⋯"按钮菜单，**无右键菜单**（桌面用户第一反应是右键）。`TapHandler` 加 `acceptedButtons: Qt.LeftButton | Qt.RightButton` 按键位分流即可。
- 菜单里没有"下一首播放 / 添加到待播列表"——应用明明有队列体系，却只能整列表替换式播放。
- QueuePanel 无"清空"，QueueRow 无单行移除（hover ✕）。待播列表只进不出。
- SongDetailDialog 的"相似歌曲"卡片有 hover 高亮但**没有任何点击行为**（`SongDetailDialog.qml:410-462`，有 HoverHandler 无 TapHandler）——假可供性，比没有 hover 更糟。要么接播放/跳详情，要么去掉 hover 态。

### W6. 搜索体验的小毛刺

- 输入框无清空"×"按钮；Esc 只失焦不清空。
- 侧栏点"搜索"导航到空搜索页但**不聚焦输入框**（Ctrl+F 反而会聚焦，`Main.qml:346-352`）——点完还得再伸手去点输入框。
- 内嵌"搜索"文字按钮的样式偏旧（QQ 是纯 pill + 放大镜）；loading 仅换文案无 spinner。

### W7. 设置页：开关用下拉框

斜体/粗体/启用/锁定这类二元项全部是 `ChoiceRow` 下拉（开/关两项）——两次点击 + 弱可供性。该用 Switch（自绘样式贴 token 即可）。SpinRow 的 "32 px" 后缀直接混在可编辑文本里（删改时要绕开后缀），建议后缀做成输入框右侧独立 Label。

### W8. 卡片网格在宽窗口下无上限膨胀

`HomeView.qml:524`：`columns: availableWidth > 560 ? 4 : ...`——560px 以上永远 4 列。1920 最大化时内容区 ≈1630px，单卡 ≈390px；2560 屏直接 ≈560px 巨图。QQ 音乐卡片固定 ≈210px、一行 5 张 + 横向翻页箭头。另外 DetailView 专辑网格用的是另一套固定 168px cell（`DetailView.qml:509`）——同一应用两套网格行为。**建议**：统一为"目标卡宽 ≈180-200px，列数 = floor(可用宽/目标宽) 钳制 2..6"。

### W9. 页内错误提示三套系统

DetailView / SearchView 用**纯红底白字通栏**（`DetailView.qml:103-120`），全局是 Banner（容器色 + 色条 + 边框，柔和得多），瞬时错误走 Snackbar。红底通栏视觉烈度等同"破坏性操作警告"，用于"加载失败"过重。统一复用 Banner 样式。

### W10. 未显式设置应用字体

`__main__.py` / Main.qml 均未设 `QFont`。Windows 默认 Segoe UI 无 CJK 字形，逐字 fallback 到雅黑——中英混排基线 / 字重不一致（Medium 在 fallback 链上常退化）。规范给出的字体栈是 PingFang SC / Microsoft YaHei。**建议**：启动期按平台设默认字体（Windows → "Microsoft YaHei UI"；Linux 交给 fontconfig），TypeScale 可加 `fontFamily` token。

### W11. 标题栏缺双击最大化

headerBar 只有 DragHandler（`Main.qml:408-415`），无双击切换最大化/还原——这是每个桌面应用的肌肉记忆（Jakob's Law）。加 `TapHandler { onDoubleTapped: root.toggleMaximized() }` 即可。顺带：返回键禁用态用 `surfaceVariantText`，和旁边正常态的窗控按钮同色——禁用与可用无法区分，禁用态应再降一级（stateDisabled 或 40% 透明度）。

### W12. 字阶 13/14 相邻

`caption=13` 与 `bodySm=14` 只差 1px，层级实际靠颜色单独撑。建议 caption 降到 12（QQ 规范次级文字 12-13px），或合并两档。

## Opportunity（建议考虑）

### O1. "正在播放"页是音乐应用的脸面，目前是全应用最素的一页

现状：72px 小封面 + 标题行 + 带边框的歌词列表，背景纯色。对照 `08-lyric-view.webp`：全窗暖色渐变 + 唱片机动画 + 橙色逐字高亮 + 简化底栏，氛围差距巨大。低成本高回报的改法（不必做唱片机）：

- 封面主色取色做背景渐变 tint，或模糊放大封面当环境背景（image provider 预模糊，避免实时 blur 开销）；

- 歌词行**点击跳播**（业界标配，现在完全没有）。

> **2026-06-11 实施记**：方案讨论后定为 **B 方案沉浸浮层**（盖侧栏+内容区、保留顶栏/播放栏、从播放栏滑入）；**用户决策不做取色、不铺封面背景，保持朴素底色**——分量感改由大封面柔投影 + 描边承担，若验收后观感仍平，后手是一层 token 级静态微渐变。双栏 + 点击跳播按建议落地，另补内容块限宽 1280（超宽防散架）。详见「🕐 待验收」表 O1 行与验收清单。

### O2. 零动效（已记录的刻意取舍，但有无感方案）

### 截图新发现（代码审查阶段未抓到）

- **W13. 模态遮罩未走 token（第三轮已修正降级）**：第二轮曾判"没有遮罩"，**判断有误**——查证 Basic 源码（`Basic/Popup.qml`），默认自带 `Overlay.modal = palette.shadow @ 50%`，第三轮歌曲详情弹窗截图中背景播放栏确实变暗了。遗留问题缩小为：遮罩强度/色值跟随系统 palette 而非我们的 `Palette.scrim` token（该 token 至今零引用），暗色下偏弱。可选打磨：给三个 Dialog 显式 `Overlay.modal: Rectangle { color: Palette.scrim }` 统一观感。
- **W14. 鼠标点击后焦点环残留**：窄窗截图里最大化按钮上挂着一圈绿色焦点环（用户刚点过还原）。所有自绘焦点环都绑的 `activeFocus`，鼠标点击同样置焦 → 点哪儿哪儿留绿圈。修法：焦点环改绑 `visualFocus`（仅键盘焦点时为真），全部组件一致替换（IconButton / NavItem / SongRow / Card / 各 Button）。
- **O3 升级（字形图标命中 emoji 字体）**：截图中侧栏 ⚙ "设置"图标呈**彩色 emoji 渲染**（蓝灰立体齿轮），完全无视 `iconColor`——字符落进了系统 emoji 字体的覆盖范围。这是 Unicode 图标方案不可控性的实证：同一套代码在不同字体环境下连"是不是单色"都保证不了。其余字形（⌂ ⌕ ♬ ⇄ ◂◂）在该机器上渲染尚可。短期可对 ⚙ 这类高危字符强制指定非 emoji 字体或换字符（如 ⛭ 亦有 emoji 风险，建议直接换 SVG），中期仍建议整套换 SVG。
- **W15. 设置页信息密度过低**：亮色设置页一屏只放下 3 个设置项——每个分区卡 = h2 标题 + 单行内容 + s5×2 内边距，约 150px 只承载一条设置。全部 ~15 项设置要滚四五屏。建议压缩分区内边距（s5→s4）、标题降为 body/medium、或合并"播放/外观"这类单条分区。
- **暗色"猜你喜欢"卡观感偏闷**：深绿 `#173c2c` 大色块在暗背景上像一块沉色板，与亮色版的清爽对不上。可考虑暗色容器改更中性的 surfaceVariant + 绿色仅做点缀，或用封面取色渐变（与 O1 同一方案族）。
- **猜你喜欢卡内容两极分布**：文字贴左、封面+播放键贴右，中间随窗口变宽无限拉开（最大化时两端相距 ~1700px），卡片读起来"断成两截"。建议给卡内容设最大宽或把封面挪到文字侧。
- **紧凑侧栏图标偏小**：64px 栏里 16px 字形图标显得迷失，建议紧凑态 icon 提到 ≥20px。

### 解除警报

- **暗色二维码可扫性**：二维码图自带白色 quiet zone，深色容器上对比充足，无需处理。
- **字体混排**：该机器上中英混排（YaHei 系）渲染干净，W10（显式设字体）降为一致性保障项而非视觉缺陷项。

### 第三轮：详情页 / 资料库 / 歌曲详情弹窗（暗色 4 张，2026-06-11）

用户补充：歌单详情页、资料库我喜欢列表、SongDetailDialog、艺人页（均暗色）。

- **B1（功能 bug，最高优先）：详情页头图永远是占位符**。歌单详情和艺人页两张截图的 168px 头图都是绿框占位（♪ / ◎），而同一歌单在首页卡片上明明有封面、弹窗头图和列表行封面也都正常。链路分析：`pushDetail(kind, id, title, subtitle)` **不传卡片上已有的 coverUrl**，头图完全依赖 `detailController.loadDetail` 拉回的详情数据（`detail_controller.py:236/259`）；详情接口的封面字段为空或字段名不一致时就永久占位。修法（双管齐下）：① `pushDetail` 增加 `coverUrl` 参数，把卡片封面作为初始值即刻显示（顺带提升感知速度）；② 排查 playlist/artist 详情 payload 的封面字段映射。
- **W14 第二次实锤**：艺人页截图里第一行的 "⋯" 按钮挂着绿色焦点环（点完菜单留下的）。
- **W16. "正在播放"行高亮只在 DetailView 生效**：DetailView 的 SongRow 绑定了 `selected:`（比对 currentSong.mid），而 **HomeView SongSection 和 LibraryView 我喜欢列表的 delegate 都没绑** `selected` —— 同一首歌在详情页里有高亮 + ♪ 标记，切到资料库就泯然众人。补两处绑定即可（截图中资料库首行的高亮其实只是 hover 态）。
- **SongDetailDialog 底部内容被齐刷刷切断**："包含此曲的歌单"卡片只露出封面，标题被弹窗下边缘切掉，且 `ScrollBar.AsNeeded` 不悬停不出现——用户很难发现下面还有内容。建议：弹窗内容高度收敛（相似歌曲/歌单二选一时减 section 间距）或底部加渐隐提示，滚动条改 `AlwaysOn`。
- **艺人页字样重复**："艺人" kind 标签 + 标题下方 subtitle 又是"艺人"，上下两行重复。subtitle 与 kindLabel 相同时应抑制。
- **正面确认**：暗色下歌单详情页（display 标题 + 双 pill 按钮 + 64px 行）和资料库 tab 页整体观感是目前完成度最高的页面；弹窗的 tags chips / facts 行也干净。绿色系在暗色全面成立——进一步佐证 C2 只需要修亮色。
